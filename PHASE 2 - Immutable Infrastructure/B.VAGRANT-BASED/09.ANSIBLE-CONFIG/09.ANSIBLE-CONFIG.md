# 9.1 What is Configuration Management?

Infrastructure provisioning answers one question:
> **What infrastructure should exist?**

Configuration management answers another:
> **What should be installed and configured inside that infrastructure?**

For example:

Vagrant creates
```
dns-01
```

Ansible configures
```
Ubuntu
↓
Update Packages
↓
Install BIND9
↓
Configure named.conf
↓
Copy Zone Files
↓
Enable Service
↓
Verify DNS
```

Everything is described as code.

# 9.3 Why Not Configure Servers Manually?

Imagine twelve servers.
Without automation you might execute:
```bash
ssh ubuntu@10.0.2.10
sudo apt install bind9
```

Then
```bash
ssh ubuntu@10.0.2.11
sudo apt install lldap
```

Then
```bash
ssh ubuntu@10.0.2.14
sudo apt install gitlab
```

Repeat dozens of commands.
Eventually every server becomes slightly different.
Manual administration does not scale.

---

## The Ansible Solution

Instead we write:
```bash
ansible-playbook site.yml
```

Ansible automatically:

- Connects to every server
- Installs required software
- Configures services
- Starts daemons
- Verifies state
- Reports failures

Every execution produces the same result.

---

# 9.4 What Makes Ansible Different?

Unlike many configuration management tools, Ansible requires:
- No agents
- No client software
- No additional daemons

Communication occurs through standard SSH.
```
Ansible Controller
        │
        │ SSH
        ▼
Ubuntu Server
```

Because SSH already exists on Linux servers, Ansible can be introduced immediately.

# 9.5 Ansible Architecture

```
                    Ansible Controller
                            │
        ┌───────────┼───────────┐
        │                  │                  │
        ▼                  ▼                  ▼
      dns-01            idm-01            gitlab-01
        │                  │                  │

       SSH                SSH                SSH
```

The Controller sends instructions.
Managed nodes execute those instructions.
No permanent connection is maintained.

# 9.9 Generate an SSH Key Pair

The Ansible controller should authenticate using SSH keys instead of passwords.

Generate a new key pair.
```bash
ssh-keygen -t ed25519
```

Accept the default location.
```
~/.ssh/id_ed25519
```

Your controller now has:
```
id_ed25519
id_ed25519.pub
```

The private key remains on the controller.
The public key will be copied to every managed node.

---

# 9.10 Copy the SSH Key

Copy the public key to the DNS server.
```bash
ssh-copy-id ubuntu@10.0.2.10
```

Repeat for every server.
```bash
ssh-copy-id ubuntu@10.0.2.11

ssh-copy-id ubuntu@10.0.2.12

ssh-copy-id ubuntu@10.0.2.13

ssh-copy-id ubuntu@10.0.2.14

...
```

After completion, SSH logins should no longer require passwords.

Verify:
```bash
ssh ubuntu@10.0.2.10
```

You should be logged in immediately using your SSH key.

# 9.15 Configure ansible.cfg

Create
```text
ansible.cfg
```

```ini
[defaults]
inventory = inventory/production/hosts.ini
roles_path = roles
collections_paths = collections
host_key_checking = False
retry_files_enabled = False
stdout_callback = yaml
interpreter_python = auto
forks = 10
timeout = 30
nocows = True
remote_user = ubuntu
deprecation_warnings = False
```

Let's examine each option.

| Option | Purpose |
|----------|----------|
| inventory | Default inventory |
| roles_path | Role search path |
| collections_paths | Collection directory |
| host_key_checking | Ignore unknown SSH host keys |
| retry_files_enabled | Disable retry files |
| stdout_callback | Cleaner output |
| interpreter_python | Auto-detect Python |
| forks | Parallel connections |
| timeout | SSH timeout |
| remote_user | Default SSH user |

These settings eliminate the need to specify command-line arguments repeatedly.

# 9.24 Using Modules

Modules are the building blocks of Ansible.
Instead of executing shell commands whenever possible, use Ansible modules.
For example, retrieve uptime.
```bash
ansible all -m command -a "uptime"
```

Gather package information.
```bash
ansible all -m package_facts
```

Gather service information.
```bash
ansible all -m service_facts
```

Modules are:
- Idempotent
- Portable
- Easier to maintain
- More reliable than shell scripts

Whenever a module exists, prefer it over raw shell commands.

Run:

Example:

# 9.27 Filtering Facts

Instead of displaying every fact, filter only the ones you need.

Display network information.
```bash
ansible all -m setup -a "filter=ansible_default_ipv4"
```

Display memory information.
```bash
ansible all -m setup -a "filter=ansible_memory_mb"
```

Display processor information.
```bash
ansible all -m setup -a "filter=ansible_processor*"
```

Display operating system.
```bash
ansible all -m setup -a "filter=ansible_distribution*"
```

Filtering facts makes troubleshooting much easier.

# 9.29 Variables

Variables make playbooks reusable.

Instead of writing
```yaml
name: Install Bind9
```

we can write
```yaml
name: Install {{ dns_package }}
```

Later,
```yaml
dns_package: bind9
```

can be replaced with
```yaml
dns_package: named
```

without modifying the playbook.

---

# 9.30 Variable Precedence

Variables can be defined in many places.
From lowest to highest priority:
```
Role Defaults
↓
Inventory
↓
group_vars
↓
host_vars
↓
Playbook Variables
↓
Task Variables
↓
Extra Variables
```

If the same variable exists in multiple locations, the highest-precedence value wins.

---

# 9.31 Using group_vars

Suppose every Kubernetes node requires the same configuration.

Instead of repeating values, create
```
inventory/production/group_vars/kubernetes_workers.yml
```

Example:
```yaml
---
container_runtime: containerd
pod_network_cidr: 10.244.0.0/16
kubernetes_version: "1.34"
```

Every Kubernetes worker automatically inherits these values.

---

# 9.32 Using host_vars

Some variables apply to only one server.

Example:
```
inventory/production/host_vars/gitlab-01.yml
```

```yaml
---
gitlab_external_url: "https://gitlab.devsecops.com"
gitlab_root_email: admin@devsecops.com
gitlab_backup_enabled: true
```

Only GitLab receives these variables.

---

# 9.33 Variable Naming

Good variable names improve readability.

Good examples:
```yaml
gitlab_version
vault_cluster_name
dns_forwarders
ldap_base_dn
harbor_hostname
```

Avoid:
```yaml
x
abc
test
tmp
var1
```

Choose descriptive names.

# 9.34 Creating the First Playbook

Inside
```

```

create
```
site.yml
```

This becomes the entry point for the entire infrastructure.
```yaml
---
- name: Configure DevSecOps Infrastructure
  hosts: all
  become: true
  gather_facts: true
```

- Become root.
- Gather system facts.
- Execute the `common` role.

# 9.35 Anatomy of a Playbook

Every playbook consists of several components.

```yaml
---
- name: Install Packages
  hosts: all
  become: true
  tasks:
    - name: Install curl
      apt:
        name: curl
        state: present
```

Let's examine the structure.

| Directive | Purpose |
|------------|----------|
| name | Description |
| hosts | Target Hosts |
| become | Privilege Escalation |
| tasks | List of Tasks |
| handlers | Restart Services |
| roles | Execute Roles |
| vars | Variables |

Understanding this structure is essential before creating larger playbooks.

---

# 9.36 Understanding Tasks

A Task performs a single action.

Examples include:
- Install a package
- Create a directory
- Copy a file
- Start a service
- Create a user
- Download software

Each task should perform one well-defined operation.

---

Example:
```yaml
- name: Install curl
  apt:
    name: curl
    state: present
```

---

# 9.37 Idempotency

Idempotency is one of the most important concepts in Ansible.

An idempotent task produces the same result no matter how many times it runs.

Example.
```yaml
apt:
  name: curl
  state: present
```

Execution 1
```
Install curl
```

Execution 2
```
Already installed
No changes
```

Execution 50
```
Already installed
No changes
```

Nothing breaks.
Nothing changes unnecessarily.
This property makes Ansible safe to execute repeatedly.

```
↓

↓

Vault

↓

↓

```

Finding a single configuration becomes challenging.

Updating services becomes risky.

Reusing code becomes nearly impossible.

To solve this problem, Ansible introduces **Roles**.

# 9.42 What is a Role?

A Role is a self-contained automation package.

Instead of writing one enormous playbook, infrastructure is divided into logical components.

For example:

```
roles/

├── common/

├── dns/

├── idm/

├── vault/

├── gitlab/

├── harbor/

├── runner/

├── kubernetes/

├── monitoring/

└── siem/
```

Each role is responsible for a single service.

This makes automation:

- Modular
- Reusable
- Easier to test
- Easier to maintain

# 9.47 The Main Task File

Open
```
roles/common/tasks/main.yml
```

Replace its contents.
```yaml
---
- name: Update package cache
  ansible.builtin.apt:
    update_cache: true
- name: Upgrade installed packages
  ansible.builtin.apt:
    upgrade: dist
- name: Install common packages
  ansible.builtin.apt:
    name:
      - curl
      - wget
      - vim
      - git
      - unzip
      - tree
      - jq
      - htop
      - net-tools
      - bash-completion
    state: present
```

Notice that every module is referenced using its Fully Qualified Collection Name (FQCN).
For example:
```
ansible.builtin.apt
```

instead of
```
apt
```

Using FQCNs is considered a best practice because it avoids ambiguity between collections.

# 9.49 Understanding Handlers

Many configuration changes require restarting services.

Example:
```
Copy sshd_config
↓
Restart SSH
```

Restarting SSH every time wastes time.
Instead, restart it only when the configuration changes.
This is exactly what Handlers do.

---

# 9.50 Creating a Handler

Open
```
roles/common/handlers/main.yml
```

Example:
```yaml
---
- name: Restart SSH
  ansible.builtin.service:
    name: ssh
    state: restarted
```

Nothing happens until another task **notifies** this handler.

---

# 9.51 Notify a Handler

Suppose we deploy a new SSH configuration.
```yaml
- name: Deploy SSH configuration
  ansible.builtin.template:
    src: sshd_config.j2
    dest: /etc/ssh/sshd_config
    owner: root
    group: root
    mode: '0644'
  notify:
    - Restart SSH
```

Execution flow.
```
Template changed?
        │
    Yes │ No
        ▼

Restart SSH
        │
     Finished
```

If nothing changes, SSH is not restarted.

# 9.55 Understanding Conditionals

Sometimes tasks should only run on certain systems.

Example:
Install BIND9 only on DNS servers.
```yaml
- name: Install BIND9
  ansible.builtin.apt:
    name: bind9
    state: present
  when:
    inventory_hostname == "dns-01"
```

Or
```yaml
when:
    "'dns' in group_names"
```

The second approach is more scalable.

# 9.56 Loops

Suppose we need to install multiple packages.
Instead of writing:
```yaml
curl
wget
vim
git
tree
jq
```

Use a loop.
```yaml
- name: Install packages
  ansible.builtin.apt:
    name: "{{ item }}"
    state: present
  loop:
    - curl
    - wget
    - vim
    - git
    - jq
    - tree
```

Loops reduce duplicated code and improve readability.

---

# 9.57 Tags

Large infrastructures may contain thousands of tasks.
Tags allow execution of only selected tasks.

Example.
```yaml
- name: Install Docker
  ansible.builtin.apt:
    name: docker.io
    state: present
  tags:
    - docker
```

Execute only Docker tasks.
```bash
ansible-playbook playbooks/site.yml --tags docker
```

Skip Docker.
```bash
ansible-playbook playbooks/site.yml --skip-tags docker
```

Tags significantly reduce execution time during development.

# 9.58 Best Practices for Roles

As our automation grows, follow these guidelines:
- One service per role.
- Keep tasks small and focused.
- Prefer Ansible modules over shell commands.
- Use variables instead of hardcoded values.
- Store reusable configuration files as templates.
- Restart services only through handlers.
- Use tags to organize large playbooks.
- Test roles independently before integrating them into `site.yml`.
- Use FQCN module names (`ansible.builtin.*`).
- Write idempotent tasks.

Following these practices keeps the automation readable, maintainable, and scalable.
