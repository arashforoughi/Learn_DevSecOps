## 33.1 DORA Metrics (DevOps Research & Assessment)

### The Four Key Metrics

```
1. DEPLOYMENT FREQUENCY (How often?)
   
   Definition: How many times per day/week can you deploy to production?
   
   Industry Benchmarks:
   ├─ Elite: Multiple deployments per day
   ├─ High: Weekly deployments
   ├─ Medium: Monthly deployments
   └─ Low: Quarterly or less
   
   Measurement:
   ├─ Tool: GitLab CI/CD logs, ArgoCD
   ├─ Query: COUNT(merge_requests.merged) / days
   └─ Target: 5+ deployments/day
   
   Improvement Actions:
   ├─ Automated testing (reduce manual verification)
   ├─ Feature flags (deploy without risk)
   ├─ Small, incremental changes (easier rollback)
   └─ Blue-green deployments (zero downtime)

2. LEAD TIME FOR CHANGES (How fast?)
   
   Definition: Time from code commit to production
   
   Measurement:
   ├─ Tool: GitLab, GitHub, Jenkins
   ├─ Calculation: production_date - commit_date
   └─ Target: < 1 hour
   
   Breakdown:
   ├─ Code review: < 10 minutes (target)
   ├─ CI pipeline: < 5 minutes (target)
   ├─ Approval: < 5 minutes (target)
   ├─ Deployment: < 10 minutes (target)
   └─ Total: < 30 minutes

3. MEAN TIME TO RECOVERY (MTTR) - How resilient?
   
   Definition: Time to restore service after failure
   
   Measurement:
   ├─ Tool: PagerDuty, incident management
   ├─ Calculation: incident_resolved_time - incident_detected_time
   └─ Target: < 1 hour
   
   Influencing Factors:
   ├─ Monitoring (detection speed)
   ├─ Alerting (notification speed)
   ├─ Runbooks (response procedure)
   ├─ Rollback capability (undo bad changes)
   └─ Team familiarity (training)

4. CHANGE FAILURE RATE (CFR) - How reliable?
   
   Definition: % of changes that cause production incidents
   
   Measurement:
   ├─ Tool: GitLab, PagerDuty
   ├─ Calculation: (failed_deployments / total_deployments) × 100
   └─ Target: < 15% (elite: < 5%)
   
   Reduction Strategies:
   ├─ Automated testing (catch issues early)
   ├─ Code review (catch logic issues)
   ├─ Staging environment (test before prod)
   ├─ Gradual rollouts (catch issues early)
   └─ Monitoring/alerting (detect issues fast)
```

## 33.2 Security-Specific Metrics

### Vulnerability Metrics

```
MEAN TIME TO REMEDIATE (MTTR):

Critical Vulnerabilities:
├─ Target: < 24 hours
├─ Measured from: Detection → Fix deployed
├─ Actions on miss:
│  ├─ Temporary mitigation (WAF rule)
│  ├─ Isolation (disable service)
│  └─ Escalation (executive notification)
└─ Root cause: Too many vulnerabilities, lack of resources

High Vulnerabilities:
├─ Target: < 7 days
├─ Medium: < 30 days
└─ Low: < 90 days

VULNERABILITY DENSITY:

Definition: Number of vulnerabilities per 1000 lines of code (KLOC)

Target: < 0.1 per KLOC

Measurement:
├─ Tool: SonarQube SAST
├─ Formula: (vulnerabilities / lines_of_code) × 1000
└─ Trend: Should be decreasing month-over-month

SCANNING COVERAGE:

├─ SAST: 100% of code
├─ DAST: 100% of APIs
├─ Container: 100% of images
├─ Dependency: 100% of dependencies
└─ Infrastructure: 100% of IaC

SLA COMPLIANCE:

Definition: % of vulnerabilities fixed within SLA

Target: > 95%

Example:
├─ 100 critical vulns: 95 fixed within 24h
├─ 150 high vulns: 142 fixed within 7d
└─ Calculate: (Compliant / Total) × 100
```

### Application Security Metrics

```
CODE QUALITY:

├─ Code Coverage
│  ├─ Target: > 80%
│  ├─ Measured: lines_executed / total_lines
│  └─ Tool: JaCoCo, CodeCov
│
├─ Defect Density
│  ├─ Target: < 2 defects per KLOC
│  ├─ Measured: defects / lines_of_code
│  └─ Tool: SonarQube
│
├─ Code Review Cycle Time
│  ├─ Target: < 24 hours
│  ├─ Measured: review_complete - code_submitted
│  └─ Tool: GitLab/GitHub
│
└─ Test Execution Time
    ├─ Target: < 15 minutes
    ├─ Measured: pipeline_end - test_start
    └─ Tool: CI/CD logs

SECURITY TESTING:

├─ SAST Findings
│  ├─ Target: 0 critical, < 5 high per release
│  └─ Tool: SonarQube
│
├─ DAST Findings
│  ├─ Target: 0 critical per release
│  └─ Tool: OWASP ZAP
│
├─ Dependency Vulnerabilities
│  ├─ Target: 0 critical
│  └─ Tool: Snyk, DependencyCheck
│
└─ Container Image Vulnerabilities
    ├─ Target: 0 critical per image
    └─ Tool: Trivy, Grype
```

## 33.3 Building Security Culture

### Security Awareness Program

```bash
#!/bin/bash
# security-culture-metrics.sh - Measure culture maturity

MONTH=$(date +%Y-%m)
REPORT_DIR="/metrics/culture/$MONTH"
mkdir -p "$REPORT_DIR"

# 1. Training Completion
echo "=== Security Training Completion ===" > "$REPORT_DIR/training.txt"
TOTAL_STAFF=$(ldapsearch -x uid=* | grep "^uid:" | wc -l)
TRAINING_COMPLETE=$(grep "$(date +%Y-%m)" /var/log/training.log | cut -d: -f1 | sort -u | wc -l)
COMPLETION_RATE=$(echo "scale=2; ($TRAINING_COMPLETE / $TOTAL_STAFF) * 100" | bc)

echo "Total staff: $TOTAL_STAFF" >> "$REPORT_DIR/training.txt"
echo "Completed training: $TRAINING_COMPLETE" >> "$REPORT_DIR/training.txt"
echo "Completion rate: $COMPLETION_RATE%" >> "$REPORT_DIR/training.txt"

# 2. Security Champions
echo "=== Security Champions ===" > "$REPORT_DIR/champions.txt"
cat /var/security/champions.txt >> "$REPORT_DIR/champions.txt"

# 3. Bug Bounty Participation
echo "=== Bug Bounty Program ===" > "$REPORT_DIR/bugbounty.txt"
curl -s "https://bugbounty-platform.com/api/reports" | jq '.total' >> "$REPORT_DIR/bugbounty.txt"

# 4. Security Incidents Caused by Human Error
echo "=== Human Error Incidents ===" > "$REPORT_DIR/human-error.txt"
grep -i "human error\|misconfiguration\|weak password" /var/log/incidents.log >> "$REPORT_DIR/human-error.txt"

# 5. Security Posture Improvements Suggested by Developers
echo "=== Developer-Suggested Improvements ===" > "$REPORT_DIR/suggestions.txt"
cat /var/security/dev-suggestions-$(date +%Y-%m).txt >> "$REPORT_DIR/suggestions.txt"

# 6. Phishing Test Results
echo "=== Phishing Simulation Results ===" > "$REPORT_DIR/phishing.txt"
echo "Month: $MONTH" >> "$REPORT_DIR/phishing.txt"
echo "Emails sent: 500" >> "$REPORT_DIR/phishing.txt"
echo "Clicked: 25" >> "$REPORT_DIR/phishing.txt"
echo "Reported: 15" >> "$REPORT_DIR/phishing.txt"
CLICKTHROUGH=$(echo "scale=2; (25 / 500) * 100" | bc)
echo "Clickthrough rate: $CLICKTHROUGH%" >> "$REPORT_DIR/phishing.txt"
echo "Reporting rate: $(echo "scale=2; (15 / 25) * 100" | bc)%" >> "$REPORT_DIR/phishing.txt"

echo "Culture metrics collected: $REPORT_DIR"
```

### Culture Maturity Model

```
LEVEL 1: Security Awareness
├─ Basic training provided
├─ Incident response playbooks exist
├─ Security team separate from dev/ops
└─ Reactive security stance

LEVEL 2: Security Integration
├─ Security champions in teams
├─ Security reviews part of PR process
├─ Some automated security scanning
└─ Security included in planning

LEVEL 3: Security Ownership
├─ Developers responsible for security
├─ Security built into every sprint
├─ Automated security testing on every commit
├─ Regular security training (quarterly)
└─ Blameless incident post-mortems

LEVEL 4: Security Excellence
├─ Security automated in pipeline
├─ Developers write security tests
├─ Threat modeling standard practice
├─ Continuous security training
├─ Security culture in hiring/promotions
└─ Innovation in security practices
```

## 33.6 Continuous Improvement Cycle

### PDCA Implementation

```
Plan-Do-Check-Act Cycle (Monthly):

MONTH 1:
├─ PLAN: Review previous month metrics
├─ DO: Implement 2 improvements
├─ CHECK: Measure results
└─ ACT: Adjust approach

MONTH 2:
├─ Implement next set of improvements
├─ Continue measuring
└─ Share learnings across teams

MONTH 3:
├─ Comprehensive assessment
├─ Quarterly stakeholder review
└─ Set targets for next quarter

EXAMPLE - April 2024:
├─ PLAN: MTTR is 45 min, target is <1h
│        ├─ Issue: Too many manual steps
│        └─ Solution: Automate incident response
├─ DO: Create automation runbooks
├─ CHECK: Measure new MTTR = 18 min
└─ ACT: Roll out automation to all teams

Example Improvements:
└─ May 2024:
   ├─ Deployment frequency: 4 → 8 times/day
   ├─ Lead time: 90 min → 42 min
   ├─ Critical vulns: 5 → 0
   └─ Team satisfaction: 6.5 → 8.2 (out of 10)
```
