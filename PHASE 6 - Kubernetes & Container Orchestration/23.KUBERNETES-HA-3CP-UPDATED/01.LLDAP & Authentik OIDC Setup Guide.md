# Complete Procedure: LLDAP + Authentik (OIDC Provider) on Ubuntu Server with Docker Compose (2026 Edition)

## Architecture, Network Topology & 2026 Version Overview

### Target Environment & Network Parameters

| Parameter                        | Value                 | Description                                            |     |
| -------------------------------- | --------------------- | ------------------------------------------------------ | --- |
| **Primary Domain**               | `devsecops.com`       | Your internal/organization domain name                 |     |
| **BIND DNS Server IP**           | `172.16.201.190`      | Authoritative DNS server resolving `devsecops.com`     |     |
| **OIDC Ubuntu Server IP**        | `172.16.201.191`      | Ubuntu host running Docker Compose (LLDAP + Authentik) |     |
| **LDAP Base DN**                 | `dc=devsecops,dc=com` | Root LDAP directory structure derived from your domain |     |
| **Authentik FQDN (Recommended)** | `auth.devsecops.com`  | DNS `A` record pointing to `172.16.201.191`            |     |
| **LLDAP Web UI FQDN (Optional)** | `lldap.devsecops.com` | DNS `A` record pointing to `172.16.201.191`            |     |

### Component Versions (2026 Stack)

* **LLDAP (`lldap/lldap:v0.6.3`)**: Acts as your lightweight, single-source-of-truth LDAP directory for `dc=devsecops,dc=com` where you create and manage users and groups via a fast web interface on `172.16.201.191:17170`.

* **Authentik (`ghcr.io/goauthentik/server:2026.8.3`)**: Acts as your Identity Provider (IdP) on `172.16.201.191:9000` (HTTP) and `172.16.201.191:9443` (HTTPS). It syncs users/groups and validates passwords against LLDAP over an internal Docker network, and exposes **OpenID Connect (OIDC) / OAuth2** endpoints to your applications.

* **PostgreSQL (`postgres:16-alpine`)**: Stores Authentik's configuration, OIDC providers, flows, and session/cache data.

  * *2026 Architecture Note*: As of Authentik `2025.10+` and `2026.x`, **Redis has been completely removed** from Authentik's architecture (replaced by native PostgreSQL caching and `LISTEN/NOTIFY` background queues), and as of `2025.12+`, Authentik uses `/data` instead of `/media` for persistent file storage. Additionally, Docker Compose v2 uses the standard `compose.yml` filename.

## Step 3: Creating the Unified `compose.yml` File (LLDAP + Authentik + PostgreSQL)

In this step, we create `/opt/sso-stack/compose.yml` on `172.16.201.191`. This file defines all four services (`lldap`, `postgresql`, `authentik-server`, and `authentik-worker`) on a shared internal bridge network named `sso-net` and configures them to use your BIND DNS server (`172.16.201.190`).

### 3.1 Key Architectural Decisions in `compose.yml`

1. **Internal Docker Network (`sso-net`)**:

   * Both `authentik-server` and `authentik-worker` communicate with `lldap` using the internal Docker hostname `ldap://lldap:3890` over `sso-net`.

   * Because LDAP communication stays strictly inside `sso-net`, we bind port `3890` only to `127.0.0.1:3890:3890` on the host so external machines cannot probe raw LDAP, while your web UI (`17170`) and Authentik (`9000` / `9443`) are reachable on `172.16.201.191`.

2. **Custom BIND DNS Injection (`dns: - ${BIND_DNS_IP}`)**:

   * Every service is configured with `dns: - 172.16.201.190` so that when Authentik or LLDAP makes outgoing requests (such as OIDC back-channel calls, webhooks, or LDAP queries to `*.devsecops.com`), it queries your BIND DNS server at `172.16.201.190`.

3. **2026 Authentik Storage & Timezone Standards**:

   * **Storage (`/data`)**: Authentik `2025.12+` and `2026.8.3` use `/data` inside the container for persistent files and icons (mounted from `./authentik-data:/data`).

   * **Timezone Warning**: Authentik requires all internal operations to run in `UTC` (and converts timestamps to local time in your browser UI). Never mount `/etc/localtime` or `/etc/timezone` into Authentik containers, as doing so causes OAuth2/OIDC token timestamp drift.

### 3.2 Create `/opt/sso-stack/compose.yml`

Ensure you are in `/opt/sso-stack` on `172.16.201.191` and run the following command to create `compose.yml`:

```
cat <<'EOF' > /opt/sso-stack/compose.yml
services:
  # ============================================================================
  # 1. LLDAP - Lightweight LDAP Directory (dc=devsecops,dc=com)
  # ============================================================================
  lldap:
    image: lldap/lldap:${LLDAP_IMAGE_TAG:-v0.6.3}
    container_name: lldap
    hostname: lldap.devsecops.com
    restart: unless-stopped
    dns:
      - ${BIND_DNS_IP:-172.16.201.190}
    ports:
      # LLDAP Web UI accessible at http://172.16.201.191:17170 or http://lldap.devsecops.com:17170
      - "${LLDAP_HTTP_PORT:-17170}:17170"
      # Raw LDAP port bound to localhost only; Authentik connects internally via sso-net (ldap://lldap:3890)
      - "127.0.0.1:${LLDAP_LDAP_PORT:-3890}:3890"
    environment:
      - TZ=${TZ:-UTC}
      - UID=${PUID:-1000}
      - GID=${PGID:-1000}
      - LLDAP_JWT_SECRET=${LLDAP_JWT_SECRET:?LLDAP_JWT_SECRET required}
      - LLDAP_KEY_SEED=${LLDAP_KEY_SEED:?LLDAP_KEY_SEED required}
      - LLDAP_LDAP_BASE_DN=${LLDAP_LDAP_BASE_DN:-dc=devsecops,dc=com}
      - LLDAP_LDAP_USER_DN=${LLDAP_LDAP_USER_DN:-admin}
      - LLDAP_LDAP_USER_EMAIL=${LLDAP_LDAP_USER_EMAIL:-admin@devsecops.com}
      - LLDAP_LDAP_USER_PASS=${LLDAP_LDAP_USER_PASS:?LLDAP_LDAP_USER_PASS required}
      - LLDAP_HTTP_URL=${LLDAP_HTTP_URL:-http://lldap.devsecops.com:17170}
      - LLDAP_ENABLE_PASSWORD_RESET=false
    volumes:
      - ./lldap-data:/data
    networks:
      - sso-net

  # ============================================================================
  # 2. PostgreSQL 16 - Database, Cache & Queue Backend for Authentik
  # ============================================================================
  postgresql:
    image: docker.io/library/postgres:16-alpine
    container_name: authentik-postgres
    restart: unless-stopped
    dns:
      - ${BIND_DNS_IP:-172.16.201.190}
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -d $${POSTGRES_DB} -U $${POSTGRES_USER}"]
      start_period: 20s
      interval: 30s
      retries: 5
      timeout: 5s
    environment:
      POSTGRES_PASSWORD: ${PG_PASS:?database password required}
      POSTGRES_USER: ${PG_USER:-authentik}
      POSTGRES_DB: ${PG_DB:-authentik}
    volumes:
      - ./postgres-data:/var/lib/postgresql/data
    env_file:
      - .env
    networks:
      - sso-net

  # ============================================================================
  # 3. Authentik Server - Core OIDC / OAuth2 Identity Provider & Web UI
  # ============================================================================
  server:
    image: ${AUTHENTIK_IMAGE:-ghcr.io/goauthentik/server}:${AUTHENTIK_TAG:-2026.8.3}
    container_name: authentik-server
    hostname: auth.devsecops.com
    restart: unless-stopped
    command: server
    dns:
      - ${BIND_DNS_IP:-172.16.201.190}
    environment:
      AUTHENTIK_POSTGRESQL__HOST: postgresql
      AUTHENTIK_POSTGRESQL__USER: ${PG_USER:-authentik}
      AUTHENTIK_POSTGRESQL__NAME: ${PG_DB:-authentik}
      AUTHENTIK_POSTGRESQL__PASSWORD: ${PG_PASS}
      AUTHENTIK_SECRET_KEY: ${AUTHENTIK_SECRET_KEY:?secret key required}
      AUTHENTIK_ERROR_REPORTING__ENABLED: ${AUTHENTIK_ERROR_REPORTING__ENABLED:-false}
    volumes:
      - ./authentik-data:/data
      - ./authentik-templates:/templates
    env_file:
      - .env
    ports:
      # Authentik HTTP & HTTPS ports on 172.16.201.191
      - "${COMPOSE_PORT_HTTP:-9000}:9000"
      - "${COMPOSE_PORT_HTTPS:-9443}:9443"
    depends_on:
      postgresql:
        condition: service_healthy
    networks:
      - sso-net

  # ============================================================================
  # 4. Authentik Worker - Background Tasks, LDAP Sync & Outpost Management
  # ============================================================================
  worker:
    image: ${AUTHENTIK_IMAGE:-ghcr.io/goauthentik/server}:${AUTHENTIK_TAG:-2026.8.3}
    container_name: authentik-worker
    restart: unless-stopped
    command: worker
    dns:
      - ${BIND_DNS_IP:-172.16.201.190}
    environment:
      AUTHENTIK_POSTGRESQL__HOST: postgresql
      AUTHENTIK_POSTGRESQL__USER: ${PG_USER:-authentik}
      AUTHENTIK_POSTGRESQL__NAME: ${PG_DB:-authentik}
      AUTHENTIK_POSTGRESQL__PASSWORD: ${PG_PASS}
      AUTHENTIK_SECRET_KEY: ${AUTHENTIK_SECRET_KEY:?secret key required}
      AUTHENTIK_ERROR_REPORTING__ENABLED: ${AUTHENTIK_ERROR_REPORTING__ENABLED:-false}
    # user: root ensures the worker can manage permissions on /data and /certs volumes
    user: root
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - ./authentik-data:/data
      - ./authentik-certs:/certs
      - ./authentik-templates:/templates
    env_file:
      - .env
    depends_on:
      postgresql:
        condition: service_healthy
    networks:
      - sso-net

networks:
  sso-net:
    name: sso-net
    driver: bridge
EOF

```

### Step 5: Integrating LLDAP into Authentik as an LDAP Directory Source

Now that both LLDAP and Authentik are running and you have created your admin/test users in LLDAP, you need to connect Authentik to LLDAP so it can synchronize users and authenticate them against your directory.

1. **Log in to Authentik Admin UI:**
* Open `[http://auth.devsecops.com:9000](http://auth.devsecops.com:9000)` (or `[http://172.16.201.191:9000](http://172.16.201.191:9000)`) and log in as `akadmin`.


2. **Navigate to LDAP Sources:**
* In the left sidebar, go to **Directory** > **LDAP Sources**.
* Click **Create**.


3. **Configure the LDAP Source Connection:**
* **Name:** `LLDAP Directory`
* **Slug:** `lldap-directory`
* **Server URI:** `ldap://lldap:389` (Since they share the same Docker network, use the service name `lldap` on port 389).
* **Base DN:** `dc=devsecops,dc=com` (Match whatever you set in your LLDAP `.env`).
* **Bind CN:** `uid=authentik-bind,ou=people,dc=devsecops,dc=com` (The service account you created in LLDAP).
* **Bind Password:** Enter the password you set for `authentik-bind`. `BindPass2026!Secure`


4. **Configure Attribute Mappings:**
* Authentik needs to know how to map LLDAP attributes to Authentik user fields.
* Under **User Property Mappings**, select the default mappings:
* `authentik default LDAP Mapping: mail`
* `authentik default LDAP Mapping: Name`
* `authentik default OpenLDAP Mapping: uid`
* `authentik default OpenLDAP Mapping: cn`


* Under **Group Property Mappings**, select:
* `authentik default LDAP Mapping: Name`
* `authentik default OpenLDAP Mapping: cn`




5. **Additional Settings:**
* **Additional User DN:** `ou=people`
* **Additional Group DN:** `ou=groups`
* **User object filter:** `(objectClass=person)`
* **Group object filter:** `(objectClass=groupOfUniqueNames)` (or `(objectClass=posixGroup)` depending on how LLDAP exposes them; `groupOfUniqueNames` is standard for LLDAP).
* **Object Uniqueness Field**: `uid`


6. **Save and Synchronize:**
* Click **Save**.
* Once saved, click on your new LDAP source and click **Sync** to pull all users and groups from LLDAP into Authentik. You can verify this by checking **Directory > Users** in Authentik—your LLDAP users should now appear there.

### Step 6: Configuring an OIDC Application & Provider in Authentik

With LLDAP users synced into Authentik, you can now create an OAuth2/OIDC Provider and link it to an Application so that external services can authenticate using Authentik.

1. **Create an OAuth2/OIDC Provider:**

* Click **Create**, select **OAuth2/OpenID Provider**, and click **Next**.
* Configure the provider settings:
* **Name:** `Demo App OIDC Provider`
* **Authentication flow:** `default-authentication-flow` (Standard UI login flow)
* **Authorization flow:** `default-provider-authorization-explicit-consent` (or implicit)
* **Client Type:** `Confidential`
* **Client ID:** Copy this value (or set a custom memorable one like `demo-app-client-id`).
* **Client Secret:** Copy the generated secret string (you will need this for your application config).
* **Redirect URIs / URLs:** Enter the callback URL of the app you are integrating (e.g., `http://localhost:8080/callback` or `[https://app.devsecops.com/oauth2/callback](https://app.devsecops.com/oauth2/callback)`).

2. **Create the Application:**

* **Launch URL:** (Optional) Enter the URL of your app.
* Click **Create**.


3. **Note down your OIDC Endpoints:**
* Authentik exposes standard OIDC discovery endpoints under your application or provider. The OpenID Configuration URL will be:

### Step 7: Verifying OIDC Login, Testing, and Production TLS / Reverse Proxy Best Practices

To make sure everything works end-to-end and is production-ready across your `devsecops.com` infrastructure:

1. **Test the OIDC Discovery Endpoint:**

```bash
curl -s http://auth.devsecops.com:9000/application/o/demo-app/.well-known/openid-configuration | jq .

```


* You should see a JSON response containing `authorization_endpoint`, `token_endpoint`, and `userinfo_endpoint`.


2. **End-to-End Authentication Flow Test:**
* Configure a test client application (such as an OAuth2 proxy, Grafana, or a local OIDC test container) pointing to your Authentik Client ID, Client Secret, and Discovery URL.
* Attempting to log into the application should redirect you to Authentik's login page (`auth.devsecops.com:9000`).
* Log in using credentials synced from LLDAP (e.g., your LLDAP user account). Authentik will validate the password against LLDAP, generate an OIDC token, and redirect you back successfully authenticated.


3. **Reverse Proxy & TLS Best Practices (Nginx):**
* In a production environment behind your BIND DNS (`172.16.201.190`), you should place Nginx in front of Authentik and LLDAP for SSL termination (`https://`).
* Example Nginx server block snippet for Authentika (`/etc/nginx/sites-available/auth.devsecops.com`):
```nginx
server {
    listen 80;
    server_name auth.devsecops.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name auth.devsecops.com;

    ssl_certificate /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    location / {
        proxy_pass http://172.16.201.191:9000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

```
