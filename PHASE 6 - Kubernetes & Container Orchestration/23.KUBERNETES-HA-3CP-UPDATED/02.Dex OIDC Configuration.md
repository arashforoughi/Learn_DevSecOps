Here is the complete, step-by-step procedure for integrating **Dex as the OIDC broker for Kubernetes**, using your newly configured Authentik/LLDAP stack as the upstream identity provider, and logging into the cluster via `kubectl` and `kubelogin`.

In this architecture, the flow is:
`kubectl` → `kubelogin` (Browser) → `Dex` (Kubernetes OIDC broker) → `Authentik` (Upstream IdP) → `LLDAP` (Credential Validation).

---

### Step 1: Create a Dex OIDC Provider in Authentik

Dex acts as a proxy for Kubernetes, so Authentik sees Dex as just another OIDC application.

1. **Log in to Authentik** as `akadmin`.
2. Go to **Applications > Providers** and click **Create** > **OAuth2/OpenID Provider**.
* **Name:** `Dex K8s Provider`
* **Client Type:** `Confidential`
* **Client ID:** `dex-kubernetes-client`
* **Client Secret:** (Copy the generated secret)
* **Redirect URIs:** `[https://dex.devsecops.com/callback](https://dex.devsecops.com/callback)` (This will be the public ingress URL you expose for Dex on K8s).
* **Advanced Protocol Settings > Subject mode:** Select `Based on User's Email` or `Based on User's Username` to ensure a consistent string is passed to Dex.


3. Go to **Applications > Applications** and click **Create**.
* **Name:** `Kubernetes Dex`
* **Slug:** `kubernetes-dex`
* **Provider:** Select `Dex K8s Provider`.



---

### Step 2: Deploy Dex on Kubernetes

Deploy Dex into your cluster (typically via Helm in the `dex` namespace) configured with an **OIDC upstream connector** pointing to Authentik, and a **static client** for Kubernetes.

Create a `dex-values.yaml` file for the Helm chart:

```yaml
config:
  issuer: https://dex.devsecops.com
  storage:
    type: kubernetes
    config:
      inCluster: true

  # The frontend UI/ingress for Dex
  web:
    http: 0.0.0.0:5556

  # Upstream Identity Provider: Authentik
  connectors:
    - type: oidc
      id: authentik
      name: Authentik (LLDAP)
      config:
        issuer: http://auth.devsecops.com:9000/application/o/kubernetes-dex/
        clientID: dex-kubernetes-client
        clientSecret: "YOUR_AUTHENTIK_CLIENT_SECRET"
        redirectURI: https://dex.devsecops.com/callback
        insecureEnableGroups: true
        # Map Authentik claims to Dex claims
        getUserInfo: true
        userIDKey: preferred_username
        userNameKey: name
        claimMapping:
          groups: groups

  # The application querying Dex (Kubernetes kube-apiserver and kubelogin)
  staticClients:
    - id: kubernetes
      name: Kubernetes API Server
      secret: "K8S_STATIC_SECRET_12345"
      redirectURIs:
        - http://localhost:8000
        - http://localhost:18000
        
ingress:
  enabled: true
  className: nginx
  hosts:
    - host: dex.devsecops.com
      paths:
        - path: /
          pathType: ImplementationSpecific
  tls:
    - secretName: dex-tls
      hosts:
        - dex.devsecops.com

```

**Deploy it via Helm:**

```bash
helm repo add dex https://charts.dexidp.io
helm install dex dex/dex -n dex --create-namespace -f dex-values.yaml

```

### Step 3: Configure the `kube-apiserver` to Trust Dex

You must configure the Kubernetes API server to trust tokens issued by Dex.

If you are using **kubeadm** or directly modifying the `kube-apiserver` manifests (usually located at `/etc/kubernetes/manifests/kube-apiserver.yaml` on control plane nodes), add the following flags to the command:

```yaml
spec:
  containers:
  - command:
    - kube-apiserver
    - --oidc-issuer-url=https://dex.devsecops.com
    - --oidc-client-id=kubernetes
    - --oidc-username-claim=preferred_username
    - --oidc-username-prefix=oidc:
    - --oidc-groups-claim=groups
    - --oidc-groups-prefix=oidc:
    # If using a custom CA, provide the CA cert so K8s can verify Dex's TLS
    # - --oidc-ca-file=/etc/kubernetes/pki/dex-ca.crt

```

*(Note: As of K8s 1.30+, Kubernetes also supports OIDC configuration via the structured `AuthenticationConfiguration` API, but the flags above remain the most common drop-in approach for many distributions).*

Once you save the file, the `kube-apiserver` pod will automatically restart to apply the flags.

### Step 4: Create Kubernetes RBAC Bindings

Kubernetes now knows how to identify the user (e.g., `oidc:arash@devsecops.com`) and their LLDAP groups (e.g., `oidc:k8s-admins`), but it does not know what they are allowed to do.

Create a `ClusterRoleBinding` to grant `cluster-admin` privileges to your LLDAP admin group.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: oidc-cluster-admin-binding
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
- kind: Group
  name: "oidc:k8s-admins"  # Matches LLDAP group name prefixed by K8s
  apiGroup: rbac.authorization.k8s.io

```

Apply it using your existing admin kubeconfig:

```bash
kubectl apply -f oidc-rbac.yaml

```

### Step 5: Configure the Client (Workstation) with `kubelogin`

Standard `kubectl` cannot open browser windows or complete OIDC OAuth2 redirects on its own. You must install the `oidc-login` plugin to handle the browser flow.

1. **Install `kubelogin**` on your local machine (macOS/Fedora) using Krew:
```bash
kubectl krew install oidc-login

```


2. **Test the configuration** using the `setup` command. This will open a browser, take you to Dex, which redirects to Authentik, where you log in with your LLDAP credentials:
```bash
kubectl oidc-login setup \
  --oidc-issuer-url=https://dex.devsecops.com \
  --oidc-client-id=kubernetes \
  --oidc-client-secret=K8S_STATIC_SECRET_12345

```


3. **Update your `~/.kube/config`:**
Configure a new user in your kubeconfig that automatically executes the `oidc-login` plugin whenever you run a `kubectl` command.
```bash
kubectl config set-credentials oidc-user \
  --exec-api-version=client.authentication.k8s.io/v1beta1 \
  --exec-command=kubectl \
  --exec-arg=oidc-login \
  --exec-arg=get-token \
  --exec-arg=--oidc-issuer-url=https://dex.devsecops.com \
  --exec-arg=--oidc-client-id=kubernetes \
  --exec-arg=--oidc-client-secret=K8S_STATIC_SECRET_12345

```


4. **Bind the user to a context and test:**
```bash
kubectl config set-context oidc-context --cluster=<your-cluster-name> --user=oidc-user
kubectl config use-context oidc-context

# Test API access
kubectl get nodes

```



If successful, your browser will open once to authenticate via Authentik, the token will be cached locally, and `kubectl get nodes` will return results successfully under your LLDAP user's identity.
