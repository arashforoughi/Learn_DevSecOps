## 28.1 Multi-Region Architecture

### Single Region (Current)

```
┌─────────────────────────────────────┐
│         REGION 1 (Primary)          │
├─────────────────────────────────────┤
│                                     │
│  ┌─────────────────────────────┐   │
│  │ 3 Control Planes (HA etcd)  │   │
│  └─────────────────────────────┘   │
│              ↓                       │
│  ┌─────────────────────────────┐   │
│  │ 2+ Worker Nodes             │   │
│  └─────────────────────────────┘   │
│              ↓                       │
│  ┌─────────────────────────────┐   │
│  │ Applications & Services     │   │
│  └─────────────────────────────┘   │
│                                     │
│  Problem: Single point of failure   │
│  If region fails: Complete outage   │
│                                     │
└─────────────────────────────────────┘
```

### Multi-Region Active-Active

```
┌─────────────────────────┐       ┌─────────────────────────┐
│  REGION 1 (US East)     │       │  REGION 2 (EU Central)  │
├─────────────────────────┤       ├─────────────────────────┤
│                         │       │                         │
│  k8s-cluster-1          │       │  k8s-cluster-2          │
│  3x CP, 2x Worker       │       │  3x CP, 2x Worker       │
│                         │       │                         │
│  Applications running   │       │  Applications running   │
│                         │       │                         │
└──────────┬──────────────┘       └────────────┬────────────┘
           │                                  │
           └──────────────┬───────────────────┘
                          │
                 ┌────────▼────────┐
                 │  Global LB      │
                 │  (traffic split │
                 │   by geo/latency)
                 └─────────────────┘
                          │
                    ┌─────▼────────┐
                    │ Users (Global)
                    └──────────────┘

Benefits:
✅ No single region SPOF
✅ Low latency (geo-distributed)
✅ Automatic failover (seconds)
✅ Load balanced by geography
✅ Multi-region HA
```

## 28.2 Kubernetes Federation (KubeFed)

### Install KubeFed

```bash
# Add Helm repo
helm repo add kubefed-charts https://raw.githubusercontent.com/kubernetes-sigs/kubefed/master/charts
helm repo update

# Install KubeFed on host cluster (Region 1)
helm install kubefed kubefed-charts/kubefed \
  --namespace kube-federation-system \
  --create-namespace

# Install on member clusters too
# (repeat for each region's cluster)
```

### Define Federated Resources

```yaml
# Deploy application across regions
apiVersion: types.kubefed.io/v1beta1
kind: FederatedDeployment
metadata:
  name: myapp-global
  namespace: default
spec:
  template:
    spec:
      replicas: 3
      selector:
        matchLabels:
          app: myapp
      template:
        metadata:
          labels:
            app: myapp
        spec:
          containers:
          - name: app
            image: harbor.devsecops.com/myapp:latest

  placement:
    clusters:
    - name: cluster-us-east   # Region 1
    - name: cluster-eu-central # Region 2
    
  overrides:
  - clusterName: cluster-us-east
    clusterOverrides:
    - path: "/spec/replicas"
      value: 3
  - clusterName: cluster-eu-central
    clusterOverrides:
    - path: "/spec/replicas"
      value: 2
```

### Federated DNS

```bash
# Install Coredns for cross-cluster DNS
helm install kubefed-dnsendpoint kubefed-charts/kubefed-coredns \
  --namespace kube-federation-system

# Apps can reference: myapp.myapp.svc.cluster.local
# DNS automatically routes to nearest cluster
```

## 28.3 Global Load Balancing

### Geo-DNS Routing

```bash
# Using Route53 (AWS) or equivalent
# mydomain.com resolves to nearest region

# Policy: Geolocation
# - Users in US → 10.0.2.25 (Region 1, US)
# - Users in EU → 10.0.3.25 (Region 2, EU)
# - Others → Primary region

# Policy: Latency-based
# - Resolve to lowest latency region
# - Automatic fallback on failure
```

### Service Mesh Global Routing (Istio)

```yaml
# Cross-cluster Istio routing
apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: myapp-global
spec:
  hosts:
  - myapp.global.svc.cluster.local
  
  ports:
  - number: 8080
    name: http
    protocol: HTTP
  
  endpoints:
  # Cluster 1 endpoint
  - address: 10.0.2.40  # k8s-worker-01, Region 1
    ports:
      http: 8080
    weight: 50  # 50% traffic
    
  # Cluster 2 endpoint
  - address: 10.0.3.40  # k8s-worker-01, Region 2
    ports:
      http: 8080
    weight: 50  # 50% traffic
    
  # Automatic failover if Region 1 down
  # VirtualService can detect and reroute
```

## 28.4 Cross-Region Disaster Recovery

### Active-Passive Failover

```
┌─────────────────┐        ┌──────────────────┐
│ REGION 1        │        │ REGION 2 (Standby)
│ (Primary)       │        │
├─────────────────┤        ├──────────────────┤
│ All traffic     │        │ Minimal traffic  │
│ Active apps     │        │ Replicated data  │
│ Live databases  │        │ Standby apps     │
│                 │        │                  │
│ RTO: 30-60 min  │        │ RPO: < 1 hour    │
└────────┬────────┘        └──────────────────┘
         │
         │ Sync data continuously
         │ (async replication)
         │
    Monitor health → If Region 1 fails
         │
         └──→ Switch DNS to Region 2
         │
         └──→ Promote Region 2 to primary
```

### Database Replication (Multi-Region)

```bash
# PostgreSQL streaming replication across regions
# Using logical replication (can cross versions/platforms)

# Region 1 (Primary)
# CREATE PUBLICATION myapp_pub FOR ALL TABLES;

# Region 2 (Subscriber)
# CREATE SUBSCRIPTION myapp_sub
#   CONNECTION 'postgresql://user@region1.example.com:5432/myapp'
#   PUBLICATION myapp_pub;

# Result:
# ✅ All changes replicated in real-time
# ✅ Can read from Region 2 (read replicas)
# ✅ Can promote Region 2 to primary if needed
# ✅ Zero downtime promotion
```

### Backup Strategy (Multi-Region)

```
Daily Backup Schedule:

Every 6 hours:
├─ Full etcd backup (Region 1)
└─ Uploaded to S3 (different region)

Every 24 hours:
├─ Full PostgreSQL backup
├─ All application state
└─ Snapshot to cold storage (Glacier)

Weekly:
├─ Test recovery procedure
├─ Restore from latest backup
└─ Verify data integrity

Monthly:
├─ Retention policy check
├─ Encryption verification
└─ Compliance audit
```

## 28.5 Cost Optimization

### Resource Right-Sizing

```
Identify Overprovisioned Resources:

BEFORE (wasting money):
Pod requests: 500m CPU, 512Mi RAM
Actual usage: 100m CPU, 128Mi RAM
Waste: 80% over-provisioned

AFTER (optimized):
Pod requests: 150m CPU, 200Mi RAM
Actual usage: 100m CPU, 128Mi RAM
Savings: 60% less cloud spend
```

### Spot Instances & Preemptible VMs

```yaml
# Use cheap, interruptible instances for non-critical workloads

apiVersion: v1
kind: Pod
metadata:
  name: batch-job
spec:
  nodeSelector:
    cloud.google.com/gke-preemptible: "true"  # GCP
  # or
    aws.amazon.com/ec2/spot: "true"  # AWS
  
  # Tolerate preemption
  tolerations:
  - key: cloud.google.com/gke-preemptible
    operator: Equal
    value: "true"
    effect: NoExecute
    tolerationSeconds: 30  # graceful shutdown time
  
  containers:
  - name: batch
    image: myapp:batch
    resources:
      requests:
        cpu: 2
        memory: 4Gi
```

### Multi-Tier Infrastructure

```
Tier 1: Premium (On-Demand VMs)
├─ Control plane nodes
├─ Stateful workloads (databases)
├─ Cost: High (~$0.50/hour)
└─ Availability: 99.99%

Tier 2: Standard (Reserved Instances)
├─ Production workloads
├─ SLA: 99.9%
├─ Cost: Medium (~$0.25/hour) - 50% discount
└─ Commitment: 1-3 year contract

Tier 3: Spot/Preemptible
├─ Batch jobs, CI/CD, dev/test
├─ Can be interrupted (low-risk work)
├─ Cost: Low (~$0.05/hour) - 80% discount
└─ Availability: 95% (best effort)

COST SAVINGS: 
Before: $1000/month
After:  $300/month (70% reduction!)
```

## 28.6 Advanced Security Patterns

### Zero-Trust Federation

```
Policy: Every access must be authenticated & authorized
        (even within same cluster or region)

Before (Trust at boundary):
┌─────────────────────────┐
│  Security boundary      │
│  ┌──────────────────┐   │
│  │ Pod-to-pod: TLS │   │  ← Authenticated
│  │ Service-to-db:  │   │
│  │ No auth (trust)  │   │  ← NOT authenticated!
│  │                  │   │
│  └──────────────────┘   │
└─────────────────────────┘

After (Zero-Trust):
┌─────────────────────────┐
│ Every connection:       │
│ ├─ Authenticated (cert) │
│ ├─ Authorized (policy)  │
│ ├─ Encrypted (mTLS)     │
│ └─ Logged (audit)       │
│                         │
│ Pod-to-pod: ✅ Auth     │
│ Pod-to-db: ✅ Auth      │
│ Pod-to-API: ✅ Auth     │
│ Everything: ✅ Logged   │
└─────────────────────────┘
```

### Network Policies (Microsegmentation)

```yaml
# Deny all traffic by default (whitelist approach)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}  # Applies to all pods
  policyTypes:
  - Ingress
  - Egress

---
# Allow specific pod-to-pod communication
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-app-to-db
spec:
  podSelector:
    matchLabels:
      app: database
  
  policyTypes:
  - Ingress
  
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: myapp
    ports:
    - protocol: TCP
      port: 5432
```

## 28.8 Compliance Across Regions

### Data Residency Requirements

```
Scenario: Data must stay in EU (GDPR)

Solution:
├─ Primary Region: EU (Germany)
├─ Secondary Region: EU (Ireland)  ← Backup only
├─ Tertiary Region: EU (Amsterdam) ← Cold storage
└─ NO data to US or non-EU regions

Implementation:
- Data classification in Vault
- Storage class selection by region
- Network policy enforcement
- Audit logging (who accessed from where)
```

## 28.9 Operational Runbooks

### Failover Procedure (Cross-Region)

```bash
# INCIDENT: Region 1 unavailable

1. DETECT (1 minute)
   └─ Alerting system detects all nodes down
      Health checks fail across the board

2. ASSESS (2 minutes)
   ├─ Check network connectivity to Region 1
   ├─ Check cloud provider status
   └─ Confirm: Region 1 is completely down

3. ACTIVATE (3 minutes)
   ├─ Change DNS to Region 2
   ├─ Promote Region 2 from hot standby to primary
   └─ Update all client configurations

4. RESTORE (5-30 minutes)
   ├─ Verify all services operational in Region 2
   ├─ Restore from latest backup if needed
   └─ Confirm application state

5. NOTIFY (30 minutes)
   ├─ Notify stakeholders of failover
   ├─ Update status page
   └─ Begin post-incident review

TOTAL RTO: < 5 minutes
TOTAL RPO: < 1 hour
```
