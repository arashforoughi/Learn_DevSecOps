## 22.2 Database Optimization

### Query Analysis

```bash
# Enable EXPLAIN ANALYZE
# Shows actual query execution plan

EXPLAIN ANALYZE
SELECT COUNT(*) FROM users 
WHERE department = 'Engineering';

# Output shows:
→ Seq Scan on users  (cost=0.00..35.50)
→ Filter: (department = 'Engineering')
→ Rows: 150 (estimated: 200)

# Problem: Seq Scan (slow! scanning all rows)
# Solution: Create index

CREATE INDEX idx_users_department 
ON users(department);

# Rerun EXPLAIN ANALYZE
# Now shows: Index Scan on idx_users_department (much faster!)
```

### Connection Pooling

PostgreSQL creates expensive connections. Use pgBouncer:

```bash
# /etc/pgbouncer/pgbouncer.ini

[databases]
devsecops = host=localhost port=5432 dbname=devsecops

[pgbouncer]
listen_port = 6432
auth_type = trust
max_client_conn = 1000
default_pool_size = 25
min_pool_size = 10
reserve_pool_size = 5

# Application connects to pgBouncer:
# psql -h localhost -p 6432 devsecops

# Benefits:
# - Connection reuse (expensive handshakes avoided)
# - Reduced connection overhead
# - Faster connection acquisition
```

### Caching Strategy

```
┌──────────────────────────────────────────────┐
│         MULTI-LAYER CACHING                 │
├──────────────────────────────────────────────┤
│                                              │
│  LAYER 1: HTTP Cache (Browser)              │
│  └─ Cache static content (1 year)           │
│     Images, CSS, JavaScript                 │
│                                              │
│  LAYER 2: CDN Cache (Edge)                  │
│  └─ Cache at geographic edge (1 day)       │
│     Static content served from nearest node │
│                                              │
│  LAYER 3: Application Cache (Redis)        │
│  └─ Cache query results (5 mins)           │
│     E.g., "Get user 123" → cached          │
│                                              │
│  LAYER 4: Database Cache (PostgreSQL)      │
│  └─ Shared buffers (automatic)             │
│     Recently accessed data stays in memory  │
│                                              │
│  LAYER 5: Disk Cache (OS)                  │
│  └─ Operating system page cache            │
│     Frequently read blocks cached          │
│                                              │
│  Result: First request slow, subsequent    │
│          requests 10-1000x faster!         │
│                                              │
└──────────────────────────────────────────────┘
```

### Redis Caching Example

```python
# Django with Redis caching

from django.core.cache import cache

# Cache computation-heavy operation
def get_user_stats(user_id):
    cache_key = f"user_stats:{user_id}"
    
    # Check cache first
    stats = cache.get(cache_key)
    if stats:
        return stats  # < 1ms (from Redis)
    
    # Not in cache, compute it
    stats = compute_user_stats(user_id)  # Takes 100ms
    
    # Store in cache for 5 minutes
    cache.set(cache_key, stats, timeout=300)
    
    return stats

# First call: 100ms (compute + cache)
# Subsequent calls (within 5 min): < 1ms (from cache)
```

## 22.3 Load Testing & Capacity Planning

### Load Testing with Apache JMeter

```bash
#!/bin/bash
# Load test: Simulate 1000 concurrent users

# Download JMeter
wget https://...jmeter.tgz
tar -xzf jmeter.tgz

  -l results.jtl \
  -j jmeter.log \
  -Jusers=1000 \
  -Jrampup=60 \
  -Jduration=300
```

## 22.4 System-Level Tuning

### Kernel Parameters

```bash
# /etc/sysctl.conf - Optimize for production

# Network tuning
net.core.somaxconn = 65535           # Listen queue size
net.ipv4.tcp_max_syn_backlog = 65535 # SYN queue size
net.ipv4.tcp_tw_reuse = 1            # Reuse TIME_WAIT sockets
net.ipv4.tcp_fin_timeout = 15        # Faster close

# Connection limits
fs.file-max = 2097152                # Max open files
fs.nr_open = 2097152                 # Per-process limit
net.ipv4.ip_local_port_range = 1024 65535

# Memory
vm.swappiness = 10                   # Prefer memory over swap
vm.overcommit_memory = 1             # Allow overcommit

# Apply changes
sysctl -p
```

### HAProxy Tuning


## 22.6 Application Layer Optimization

### Connection Pooling in Applications

```python
# SQLAlchemy with pool_pre_ping

from sqlalchemy import create_engine

engine = create_engine(
    'postgresql://user:pass@localhost/db',
    
    # Connection pooling
    pool_size=20,              # Default connections
    max_overflow=40,           # Extra connections if needed
    pool_timeout=30,           # Timeout waiting for connection
    
    # Health checks
    pool_pre_ping=True,        # Verify connection alive before use
    pool_recycle=3600,         # Recycle after 1 hour
    
    # Performance
    echo_pool=False,           # Don't log pool activity
    echo=False,                # Don't log SQL
)
```

### Async/Await for I/O

```python
# FastAPI with async handlers (don't block)

from fastapi import FastAPI
import asyncio

app = FastAPI()

@app.get("/api/users/{user_id}")
async def get_user(user_id: int):
    # Async database query (doesn't block)
    user = await db.query(
        "SELECT * FROM users WHERE id = %s",
        (user_id,)
    )
    
    # Parallel requests to other services
    orders = await fetch_orders(user_id)
    payments = await fetch_payments(user_id)
    
    # All happen concurrently (fast!)
    return {
        "user": user,
        "orders": orders,
        "payments": payments
    }

# vs synchronous (slow - waits for each):
def get_user_sync(user_id: int):
    user = db.query("SELECT * FROM users WHERE id = %s", (user_id,))
    orders = fetch_orders(user_id)  # Wait for this
    payments = fetch_payments(user_id)  # Then wait for this
    # Total time = sum of all operations
```
