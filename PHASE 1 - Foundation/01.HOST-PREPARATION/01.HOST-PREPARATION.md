# Chapter 01 — Host Preparation & Hypervisor Setup

## 1.1 Why This Step Matters

Most people skip straight to installing tools. They create VMs with default settings, use whatever network the hypervisor assigns, and then spend days troubleshooting why two services can't talk to each other — because their IPs keep changing.

In a professional environment, infrastructure planning comes _before_ provisioning. You decide on addressing, naming, and network topology before a single server boots.

🏗️ **Real-World Analogy:** Think of this as the architectural drawing phase of a building project. You don't pour concrete before you know where the walls go. A well-planned network is the equivalent of a well-drawn blueprint — it saves ten times the time later when you're integrating a dozen services.

💡 **Key Takeaway:** Static IPs, consistent hostnames, and a planned network topology are not optional niceties — they are prerequisites for a reliable lab.

## 1.2 Hypervisor Options

A hypervisor is software that lets your physical machine run multiple virtual machines simultaneously. Each VM gets its own CPU time, memory, and storage — isolated from each other and from the host.

### 1.2.1 Choosing the Right Hypervisor for This Lab

|Hypervisor|Type|Host OS|Cost|Best For|
|---|---|---|---|---|
|**KVM/QEMU + libvirt**|Type-1 (on Linux)|Linux|Free|Production-like, best performance|
|**VirtualBox**|Type-2|Linux / macOS / Windows|Free|Beginners, quick setup|
|**VMware Workstation/Fusion**|Type-2|Linux / macOS / Windows|Paid|Advanced networking, snapshots|
|**Proxmox VE**|Type-1|Bare metal|Free|Dedicated lab server, web UI|
|**UTM (Apple Silicon)**|Type-2 (QEMU)|macOS ARM|Free|M1/M2/M3 Mac users|

> **This lab is written primarily for KVM/QEMU on Linux**, because:
> 
> - It has the lowest overhead (near-native performance)
> - `virsh` and `virt-install` commands are scriptable (which matters for Packer/OpenTofu)
> - It is the standard in professional DevOps environments
> 
> VirtualBox instructions are provided where they differ significantly.

### 1.2.2 Hardware Requirements

|Component|Minimum|Recommended|
|---|---|---|
|CPU|8 cores with VT-x/AMD-V|16+ cores|
|RAM|32 GB|64 GB|
|Disk|500 GB SSD|1 TB NVMe SSD|
|Network|1 Gbps|1 Gbps (wired preferred)|

**Check if your CPU supports hardware virtualization:**

```bash
# On Linux — checks for Intel VT-x or AMD-V flags
$ grep -E --color '(vmx|svm)' /proc/cpuinfo | head -3
```

```
# Expected output (Intel):
→ flags : ... vmx ...

# Expected output (AMD):
→ flags : ... svm ...
```

> ⚠️ If you see no output, hardware virtualization may be disabled in BIOS. Reboot into BIOS/UEFI settings and look for "Intel VT-x", "Intel Virtualization Technology", or "AMD-V / AMD Virtualization" and enable it.

## 1.3 Installing KVM/QEMU on Ubuntu 24.04 (Recommended Path)

> **Why Ubuntu 24.04 LTS?** Long-Term Support means five years of security patches. Stable package repositories. Excellent KVM integration. The same OS we use for every VM in the lab — consistency reduces cognitive load.

### Step 1 — Update the Host System

```bash
# Always start with a fully updated system.
# Running outdated packages means running known vulnerabilities.
$ sudo apt update && sudo apt upgrade -y
```

```
# What this does:
# apt update      → Refreshes the list of available packages from repositories
# apt upgrade -y  → Installs all available updates, -y auto-confirms
```

🔐 **Security Note:** `apt upgrade` patches your host kernel and libraries. A lab with an unpatched host is not a security lab — it is a security liability.

### Step 2 — Install KVM and Management Tools

```bash
# Install KVM, QEMU, libvirt (the API layer), and management utilities
$ sudo apt install -y \
    qemu-kvm \
    libvirt-daemon-system \
    libvirt-clients \
    bridge-utils \
    virt-manager \
    virtinst \
    cpu-checker \
    guestfs-tools
```

**What each package does:**

|Package|Purpose|
|---|---|
|`qemu-kvm`|The actual hypervisor and hardware emulation engine|
|`libvirt-daemon-system`|Background daemon that manages VMs via an API|
|`libvirt-clients`|CLI tools: `virsh`, for managing VMs from the terminal|
|`bridge-utils`|Tools to create and manage network bridges|
|`virt-manager`|Graphical VM manager (useful for initial setup)|
|`virtinst`|`virt-install` command — creates VMs from the command line|
|`cpu-checker`|`kvm-ok` command — verifies your CPU supports KVM|
|`guestfs-tools`|Tools to inspect and modify VM disk images without booting|

### Step 3 — Verify KVM is Working

```bash
# Verify the CPU and kernel support KVM acceleration
$ kvm-ok
```

```
# Expected output:
→ INFO: /dev/kvm exists
→ KVM acceleration can be used
```

> ⚠️ If you see `KVM acceleration can NOT be used`, go back to BIOS and enable virtualization, or check that the `kvm_intel` (or `kvm_amd`) kernel module is loaded: `lsmod | grep kvm`

### Step 4 — Add Your User to the libvirt Group

```bash
# Without this, you have to run every virsh command with sudo.
# Adding yourself to the libvirt and kvm groups lets you manage VMs as a normal user.
$ sudo usermod -aG libvirt,kvm $USER

# Apply group membership immediately (or log out and back in)
$ newgrp libvirt
```

> **Why this matters from a security standpoint:** You want to run VM management commands as your normal user, not root. Doing everything as root violates the principle of least privilege — if your session is compromised, the attacker immediately has root on the host.

### Step 5 — Enable and Verify the libvirt Service

```bash
# Enable libvirtd to start automatically on boot
$ sudo systemctl enable --now libvirtd

# Check it's running
$ sudo systemctl status libvirtd
```

```
# Expected output (truncated):
→ ● libvirtd.service - Virtualization daemon
→      Active: active (running) since ...
```

```bash
# Verify you can talk to the hypervisor as your normal user
$ virsh list --all
```

```
# Expected output (empty lab — no VMs yet):
→  Id   Name   State
→ ----------------------
```

## 1.4 Designing the Lab Network

> 🏗️ **Analogy:** Think of your lab network like a private office building. The host machine is the building itself and the router at the entrance. Each VM is a room inside. The network we design here is the internal wiring — who can reach whom, and through what doors.

### 1.4.1 Network Types in KVM

KVM supports several network modes. Choosing the wrong one is a common mistake:

|Network Mode|VMs Talk to Host?|VMs Talk to Each Other?|VMs Reach Internet?|Use For|
|---|---|---|---|---|
|**NAT (default)**|Yes|Yes|Yes (via NAT)|Simple testing|
|**Bridged**|Yes|Yes|Yes (direct)|Production-like|
|**Host-only**|Yes|Yes|No|Isolated lab ✅|
|**Isolated**|No|Yes|No|DMZ segments|

**We use a combination:**

- **Host-only / isolated network (`10.0.2.0/24`)**: Primary lab network. All VMs communicate here.
- **NAT bridge**: Optional secondary interface on VMs that need package downloads during setup.

### 1.4.2 Creating the Lab Network

```bash
# Create a network definition file for libvirt
# This is XML — libvirt's configuration format
$ cat > /tmp/lab-network.xml << 'EOF'
<network>
  <name>devsecops-lab</name>
  <bridge name="virbr-lab" stp="on" delay="0"/>
  <ip address="10.0.2.1" netmask="255.255.255.0">
    <dhcp>
      <!-- We define static DHCP reservations so IPs never change -->
      <!-- But we will NOT use DHCP in the lab — static IPs on all VMs -->
    </dhcp>
  </ip>
</network>
EOF
```

```bash
# Define the network in libvirt
$ virsh net-define /tmp/lab-network.xml
```

```
# Expected output:
→ Network devsecops-lab defined from /tmp/lab-network.xml
```

```bash
# Start the network
$ virsh net-start devsecops-lab

# Set it to auto-start on host reboot
$ virsh net-autostart devsecops-lab

# Verify it's active
$ virsh net-list --all
```

```
# Expected output:
→  Name            State    Autostart   Persistent
→ ------------------------------------------------
→  devsecops-lab   active   yes         yes
→  default         active   yes         yes
```

```bash
# Verify the bridge interface was created on the host
$ ip addr show virbr-lab
```

```
# Expected output:
→ 5: virbr-lab: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
→     inet 10.0.2.1/24 brd 10.0.2.255 scope global virbr-lab
```

> 💡 **Key Takeaway:** `10.0.2.1` is now your host machine's IP on the lab network. Every VM you create on `devsecops-lab` will be able to reach the host at `10.0.2.1`. The host can reach every VM. VMs cannot reach the internet by default (which is exactly what we want for a security lab).

### 1.4.3 Enabling Host-to-VM Forwarding (for Package Downloads)

During initial VM setup, VMs need to download packages. We will temporarily enable NAT forwarding during the provisioning phase, then lock it down.

```bash
# Check current IP forwarding state
$ sysctl net.ipv4.ip_forward
```

```
# Expected output:
→ net.ipv4.ip_forward = 1
```

> libvirt usually enables this automatically. If it shows `0`, enable it:

```bash
# Enable IP forwarding temporarily
$ sudo sysctl -w net.ipv4.ip_forward=1

# Make it persistent across reboots
$ echo "net.ipv4.ip_forward = 1" | sudo tee /etc/sysctl.d/99-ip-forward.conf
```

## 1.5 Preparing the Base Ubuntu 24.04 ISO

Every VM in this lab runs Ubuntu 24.04 LTS. Instead of downloading the ISO 12 times, we download it once, verify it, and keep it as our single source of truth.

### Step 1 — Download Ubuntu 24.04 Server ISO

```bash
# Create a directory for your ISOs
$ sudo mkdir -p /var/lib/libvirt/isos
$ cd /var/lib/libvirt/isos

# Download Ubuntu 24.04.4 LTS Server (the "no-GUI" version — smaller and faster)
$ wget https://releases.ubuntu.com/22.04/ubuntu-24.04.4-live-server-amd64.iso
```

> **Why the server edition?** No graphical interface means less software installed, which means smaller attack surface. Every package installed is a package that could have a vulnerability. Install only what you need.

### Step 2 — Verify the ISO (Critical Security Step)

```bash
# Download the official SHA256 checksums and signature
$ wget https://releases.ubuntu.com/22.04/SHA256SUMS
$ wget https://releases.ubuntu.com/22.04/SHA256SUMS.gpg

# Verify the checksum file's GPG signature
# This proves Ubuntu signed these checksums — not a malicious actor
$ gpg --keyserver hkp://keyserver.ubuntu.com --recv-keys \
    0x843938DF228D22F7B3742BC0D94AA3F0EFE21092

$ gpg --verify SHA256SUMS.gpg SHA256SUMS
```

```
# Expected output (look for "Good signature"):
→ gpg: Signature made ...
→ gpg: Good signature from "Ubuntu CD Image Automatic Signing Key ..."
```

```bash
# Now verify the ISO matches the checksum
$ sha256sum -c SHA256SUMS 2>/dev/null | grep ubuntu-24.04.4-live-server-amd64.iso
```

```
# Expected output:
→ ubuntu-24.04.4-live-server-amd64.iso: OK
```

> 🔐 **Security Note:** This two-step verification (GPG signature first, then checksum) is called a "chain of trust." We verify that Ubuntu signed the checksum file, then verify the ISO matches that signature. A corrupted or tampered ISO would fail the checksum step. Skipping this is how supply-chain attacks succeed.

## 1.6 Creating a Base "Template" VM

Rather than installing Ubuntu from scratch 12 times, we create one base VM, configure it with common settings, then clone it for each role. This is the manual version of what Packer automates in Phase 2.

### Step 1 — Create the Base VM

```bash
# Create the base template VM
# Read every flag — each one has a purpose
$ virt-install \
  --name "ubuntu-24.04-base" \
  --ram 2048 \
  --vcpus 2 \
  --disk path=/var/lib/libvirt/images/ubuntu-24.04-base.qcow2,format=qcow2,size=20 \
  --os-variant ubuntu22.04 \
  --network network=devsecops-lab,model=virtio \
  --graphics none \
  --console pty,target_type=serial \
  --cdrom /var/lib/libvirt/isos/ubuntu-24.04.4-live-server-amd64.iso \
  --extra-args "console=ttyS0,115200n8 serial"
```

**Flag breakdown:**

| Flag              | Value                   | Reason                                                |
| ----------------- | ----------------------- | ----------------------------------------------------- |
| `--name`          | `ubuntu-24.04-base`     | Template identifier                                   |
| `--ram`           | `2048`                  | 2 GB — enough for installation                        |
| `--vcpus`         | `2`                     | 2 virtual CPUs                                        |
| `--disk`          | `qcow2, 20GB`           | QCOW2 = thin-provisioned (only uses what it needs)    |
| `--os-variant`    | `ubuntu22.04`           | Tells QEMU to use optimal settings for this OS        |
| `--network`       | `devsecops-lab, virtio` | Our lab network; virtio = paravirtualized (faster)    |
| `--graphics none` | —                       | No GUI. Serial console only (more secure, scriptable) |
| `--console pty`   | —                       | Attach the terminal to the VM's serial port           |

> **Why `qcow2` format?** QCOW2 (QEMU Copy-On-Write version 2) is a disk image format that only allocates disk space as data is written — so a 20 GB disk might only use 3 GB initially. It also supports snapshots, which are essential for a lab environment where you want to roll back to a clean state.

### Step 2 — Ubuntu Server Installation Choices

During the installation wizard, make these specific selections:

```

Keyboard:         Your layout
Network:          Configure manually (we'll fix in a moment)
Storage:          Use entire disk (LVM)
  ├─ Custom LVM layout if you want practice
  └─ Default is fine for the base template

  Name:           DevSecOps Admin
```

> **Why create a `devops` user?** We will use this account consistently across all VMs, managed through LDAP (set up in Chapter 05). Having a consistent admin username simplifies automation. In Phase 2, Ansible uses this account for configuration.

```bash
# Configure SSH hardening on the base image
# This applies to every VM we clone from this template
cat > /etc/ssh/sshd_config.d/hardening.conf << 'EOF'
# Disable root login via SSH — always use a named account
PermitRootLogin no

# Disable password authentication — require SSH keys
# (We enable this fully after setting up key distribution in Chapter 03)
PasswordAuthentication yes   # Temporarily yes for initial setup

# Disable empty passwords
PermitEmptyPasswords no

# Only allow SSH protocol 2 (protocol 1 is insecure)
Protocol 2

# Set idle timeout — disconnect idle sessions after 10 minutes
ClientAliveInterval 300
ClientAliveCountMax 2

# Limit login attempts
MaxAuthTries 3

# Only allow our devops user via SSH
AllowUsers devops

# Disable X11 forwarding (no GUI, so no need — reduces attack surface)
X11Forwarding no

# Log level — INFO is default but we increase for audit purposes
LogLevel VERBOSE
EOF

systemctl restart sshd
systemctl status sshd
```

```bash
# Enable UFW (firewall) with a strict default policy
ufw default deny incoming    # Block all inbound by default
ufw default allow outgoing   # Allow all outbound by default
ufw allow 22/tcp             # Allow SSH
ufw --force enable           # Enable without interactive prompt
ufw status verbose
```

```
# Expected output:
→ Status: active
→
→ To                         Action      From
→ --                         ------      ----
→ 22/tcp                     ALLOW IN    Anywhere
```

> ⚠️ **We are enabling the firewall on the base template.** Every VM cloned from this will start with SSH allowed and everything else blocked. Each role-specific VM will then open only the ports it needs. This is defense-in-depth at the infrastructure level.

```bash
# Configure fail2ban to protect SSH
cat > /etc/fail2ban/jail.local << 'EOF'
[DEFAULT]
# Ban an IP for 1 hour after 5 failed attempts in 10 minutes
bantime  = 3600
findtime = 600
maxretry = 5

[sshd]
enabled = true
port    = ssh
logpath = %(sshd_log)s
backend = %(syslog_backend)s
EOF

systemctl enable --now fail2ban
fail2ban-client status
```

```
# Expected output:
→ Status
→ |- Number of jail: 1
→ `- Jail list:   sshd
```

```bash
# Set the hostname format we'll use for all VMs
# (The actual hostname is set per-VM after cloning)
hostnamectl set-hostname ubuntu-base

# Clean up and prepare for cloning (remove machine-specific identifiers)
truncate -s 0 /etc/machine-id
rm -f /var/lib/dbus/machine-id
ln -s /etc/machine-id /var/lib/dbus/machine-id

# Remove SSH host keys — each cloned VM generates new unique keys on first boot
rm -f /etc/ssh/ssh_host_*

# Clear command history
history -c && history -w

# Shutdown — we clone from the powered-off state
shutdown -h now
```

> **Why remove `/etc/machine-id`?** Each Linux system has a unique machine ID used by systemd, DHCP, and other services. If you clone a VM without clearing this, all your clones share the same machine ID, causing conflicts. An empty file tells systemd to generate a new ID on first boot.

## 1.7 Cloning the Base Template to Role-Specific VMs

Now we clone the base template 12 times, one per role. This is the moment the lab comes alive.

### Create a Clone Script

```bash
# Save this to your host machine
cat > ~/lab/scripts/create-vm.sh << 'SCRIPT'
#!/bin/bash
# Usage: ./create-vm.sh <hostname> <ip> <ram_mb> <vcpus> <disk_gb>
# Example: ./create-vm.sh sec-dns-01 10.0.2.10 2048 2 20

set -euo pipefail

HOSTNAME="$1"
IP="$2"
RAM="$3"
VCPUS="$4"
DISK_GB="$5"
BASE_IMAGE="/var/lib/libvirt/images/ubuntu-22.04-base.qcow2"
VM_IMAGE="/var/lib/libvirt/images/${HOSTNAME}.qcow2"
NETWORK="devsecops-lab"

echo "🚀 Creating VM: ${HOSTNAME} (${IP}) — ${RAM}MB RAM, ${VCPUS} vCPU, ${DISK_GB}GB"

# Clone the base image (creates a new independent copy)
sudo qemu-img create -f qcow2 -b "${BASE_IMAGE}" -F qcow2 "${VM_IMAGE}" "${DISK_GB}G"

# Define the VM in libvirt using virt-install
sudo virt-install \
  --name "${HOSTNAME}" \
  --ram "${RAM}" \
  --vcpus "${VCPUS}" \
  --disk path="${VM_IMAGE}",format=qcow2 \
  --os-variant ubuntu22.04 \
  --network network="${NETWORK}",model=virtio \
  --graphics none \
  --console pty,target_type=serial \
  --import \
  --noautoconsole

echo "✅ VM ${HOSTNAME} created. Starting VM..."
sudo virsh start "${HOSTNAME}"

echo ""
echo "📋 Next steps:"
echo "   1. Connect: virsh console ${HOSTNAME}"
echo "   2. Set hostname: hostnamectl set-hostname ${HOSTNAME}.devsecops.com"
echo "   3. Set static IP: ${IP}/24, gateway: 10.0.2.1"
echo "   4. Set DNS: 10.0.2.10 (after sec-dns-01 is running)"
SCRIPT

chmod +x ~/lab/scripts/create-vm.sh
```

## 1.8 Configuring Static IPs on Each VM

Each VM needs a static IP address that will never change. We use **Netplan** (Ubuntu 24.04's network configuration tool) to set these.

### Pattern — Apply This to Every VM

Log into each VM via the serial console (`virsh console <vm-name>`) and apply the appropriate IP configuration. Here is the pattern for `sec-dns-01`:

```bash
# Inside sec-dns-01
sudo -i

# Identify the network interface name
ip link show
```

```
# Expected output (interface name varies — usually 'enp1s0' or 'ens3'):
→ 1: lo: <LOOPBACK,UP,LOWER_UP> ...
→ 2: enp1s0: <BROADCAST,MULTICAST,UP,LOWER_UP> ...
```

```bash
# Write the static IP configuration
# Replace 'enp1s0' with your actual interface name
cat > /etc/netplan/00-lab-network.yaml << 'EOF'
network:
  version: 2
  renderer: networkd
  ethernets:
    enp1s0:
      dhcp4: false
      addresses:
        - 10.0.2.10/24        # Static IP for this VM
      routes:
        - to: default
          via: 10.0.2.1       # Default gateway = host machine
      nameservers:
        addresses:
          - 10.0.2.10         # DNS = ourselves (for sec-dns-01 only!)
          - 8.8.8.8           # Fallback to Google DNS until BIND9 is configured
        search:
          - devsecops.com
EOF

# Apply the configuration
netplan apply

# Verify the IP was applied
ip addr show enp1s0
```

```
# Expected output:
→ 2: enp1s0: <BROADCAST,MULTICAST,UP,LOWER_UP> ...
→     inet 10.0.2.10/24 brd 10.0.2.255 scope global enp1s0
```

## 1.9 Setting Up SSH Key-Based Access

Typing a password every time you SSH into a VM is slow and less secure than key-based authentication. We generate one SSH key pair on the host and distribute the public key to every VM.

```bash
# On the HOST machine — generate a dedicated lab SSH key pair
$ ssh-keygen -t ed25519 -C "devsecops-lab-$(date +%Y)" -f ~/.ssh/devsecops-lab

# This creates:
# ~/.ssh/devsecops-lab      ← private key (NEVER share this)
# ~/.ssh/devsecops-lab.pub  ← public key (copy to every VM)
```

> **Why Ed25519?** It uses elliptic curve cryptography and is currently considered the most secure and efficient SSH key type. Older RSA 2048-bit keys are mathematically adequate but slower. Ed25519 keys are also smaller and faster to verify, which matters at scale.

## 1.10 Validation Script — Chapter 01

Run this from your host machine. Every check should pass before moving to Chapter 02.

```bash
#!/bin/bash
# /home/user/lab/scripts/validate-chapter-01.sh
# Run from: HOST machine

set -euo pipefail

PASS=0
FAIL=0

check() {
    local description="$1"
    local command="$2"
    local expected="$3"

    result=$(eval "$command" 2>/dev/null || true)
    if echo "$result" | grep -q "$expected"; then
        echo "  ✅ PASS: $description"
        ((PASS++))
    else
        echo "  ❌ FAIL: $description"
        echo "         Expected: '$expected'"
        echo "         Got:      '$result'"
        ((FAIL++))
    fi
}

echo "========================================="
echo " Chapter 01 Validation — Host & Network  "
echo "========================================="

echo ""
echo "--- Hypervisor ---"
check "KVM module loaded" "lsmod | grep kvm" "kvm"
check "libvirtd running" "systemctl is-active libvirtd" "active"
check "Lab network active" "virsh net-list" "devsecops-lab.*active"

echo ""
echo "--- Network Bridge ---"
check "virbr-lab interface exists" "ip addr show virbr-lab" "10.0.2.1"
check "IP forwarding enabled" "sysctl net.ipv4.ip_forward" "= 1"

echo ""
echo "--- VM Status ---"
VMS="sec-dns-01 sec-idm-01 sec-edge-01 sec-vault-01 sec-vcs-01 \
     sec-appsec-01 sec-registry-01 k8s-master-01 k8s-worker-01 \
     k8s-worker-02 sec-obs-01 sec-siem-01"

for VM in $VMS; do
    check "VM ${VM} exists" "virsh list --all" "${VM}"
done

echo ""
echo "--- SSH Connectivity ---"
for VM in sec-dns-01 sec-idm-01 sec-edge-01; do
    check "SSH to ${VM}" "ssh -o ConnectTimeout=5 ${VM} 'echo ok'" "ok"
done

echo ""
echo "--- Results ---"
echo "  Passed: ${PASS}"
echo "  Failed: ${FAIL}"

if [ "$FAIL" -eq 0 ]; then
    echo ""
    echo "🎉 All checks passed! Ready for Chapter 02."
else
    echo ""
    echo "⚠️  ${FAIL} check(s) failed. Fix issues before proceeding."
    exit 1
fi
```

## 1.11 Troubleshooting

### Problem: `kvm-ok` says KVM cannot be used

**Cause:** Hardware virtualization not enabled in BIOS. **Fix:** Reboot into BIOS/UEFI. Look for "Intel VT-x", "SVM Mode", or "AMD Virtualization". Enable it. Save and reboot.

### Problem: `virsh net-start devsecops-lab` fails with "already exists"

**Cause:** A previous attempt defined but didn't start the network. **Fix:**

```bash
$ virsh net-destroy devsecops-lab
$ virsh net-undefine devsecops-lab
$ virsh net-define /tmp/lab-network.xml
$ virsh net-start devsecops-lab
```

### Problem: VM has no network after cloning

**Cause:** Interface name may differ. Netplan config references the wrong interface. **Fix:**

```bash
# Inside the VM, find the real interface name
ip link show
# Update /etc/netplan/00-lab-network.yaml with the correct interface name
netplan apply
```

### Problem: `ssh-copy-id` fails — "Connection refused"

**Cause:** SSH is not running on the VM, or the VM hasn't fully booted. **Fix:**

```bash
# Check if the VM is running
virsh list --all
# If it shows 'shut off', start it:
virsh start <vm-name>
# Wait 30 seconds, then try again
```

### Problem: VM boots but shows "cloud-init" errors

**Cause:** Ubuntu's cloud-init runs on first boot and may conflict with cloned images. **Fix:**

```bash
# Inside the VM, disable cloud-init (we don't use it in this lab)
systemctl disable cloud-init
touch /etc/cloud/cloud-init.disabled
```
